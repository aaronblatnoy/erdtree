## 0. CONTEXT & GOALS

Problem statement
  Erdtree ships with 11 registered tools (services, packages, logs, network,
  firewall, users, disk, processes, hardware, files, docs). Radagon (the
  data-center tier, the core business) needs the full RHEL 9 sysadmin surface
  — SELinux, LVM/stratis/NFS, containers, scheduling, subscription-manager,
  compliance (sssd/pam/aide/fapolicyd), web/db services, backup. This plan
  builds ~44 new tool modules, each following the frozen ToolSpec contract,
  each with its finetune scenario corpus + Rocky-9 output simulator + test,
  and extends the safety classifier so the new destructive verbs (virsh
  undefine, stratis destroy, podman rm, pvremove, etc.) gate as DESTRUCTIVE.

Success criteria (measurable)
  - ~44 new modules in core/tools/, each self-registering, each passing its
    own tests/test_tools_<name>.py.
  - registry.list_tools() returns 11 + ~44 = ~55 unique names, no dup-name
    ValueError at import.
  - finetune/simulate/__init__.py import-time COMPLETENESS ASSERT passes for
    every (tool, op) pair in the live registry.
  - Each new tool has >= 40 scenarios; finetune/validate.py exits 0 (MISS rate
    <= 0.5%, zero I2 violations, ALL tools covered — threshold bumped from 11).
  - permissions.classify() returns DESTRUCTIVE (-> CONFIRM_TYPED, REFUSE when
    non-interactive) for every new data-loss / lockout verb enumerated in the
    Phase 0 manifest. Verified by an adversarial consensus review.
  - Full pytest suite green; test_output_hygiene / I2 scan clean across all new
    modules; no network import anywhere in core/tools/ (I1).

Non-goals (explicitly out of scope)
  - Rebuilding or refactoring the 11 existing tools (services, packages, logs,
    network, firewall, users, disk, processes, hardware, files, docs).
  - Changing the frozen shared contract in core/tools/__init__.py (ToolSpec,
    OpSpec, ArgSpec, ToolResult, ToolRegistry, run_subprocess) — ADDITIVE ONLY.
  - Changing repl.py's synthesize_command() rendering or the router.
  - Live end-to-end runs against Ollama/mossad (DEFERRED-TO-MOSSAD, as today).
  - Fine-tuning the model itself (this produces the training-data slices; the
    actual SFT run in finetune/ is a separate initiative).
  - Any GUI, any cloud/network feature (violates I1).

Assumptions made
  - A1: The vertical-slice unit is the right granularity — one agent produces
    ALL of {core/tools/<name>.py, finetune/scenarios/<name>.py,
    finetune/simulate/<name>.py, tests/test_tools_<name>.py} for one tool,
    then a later serialized phase wires the aggregators. Rationale: op names +
    arg schemas are freshest in the authoring agent's context (INV-schema-sync
    is trivially satisfied), and new-file creation is collision-free.
  - A2: OpSpec.permission_class is ADVISORY (documented in disk.py/firewall.py
    headers); the AUTHORITATIVE gate is permissions.classify() over the faithful
    command line. Therefore correctness of gating for NEW verbs REQUIRES the
    Phase 1 classifier extension — the per-op class alone is not sufficient.
  - A3: The aggregators (finetune/scenarios/__init__.py, finetune/simulate/
    __init__.py) keep their EXPLICIT per-tool imports (no glob/auto-discovery)
    — the codebase deliberately avoids "plugin magic" (see ToolRegistry
    docstring). We honor that: wiring is explicit and serialized.
  - A4: Tool-name uniqueness — new names (nmcli, nftables, dns, routing, bond,
    lvm, stratis, ...) do NOT collide with the 11 existing names. Functional
    OVERLAP with existing network/firewall/disk tools is acceptable (different
    registry name = no collision), but Phase 0 produces an overlap map so we
    don't duplicate behavior confusingly.
  - A5: Target count is ~44 tools (enumerated below); the request said "35-40".
    If scope must shrink, the Phase→tool table is the cut list.

## 1. ARCHITECTURE OVERVIEW

How this fits the existing system
  Each tool is a leaf that self-registers into the module-level `registry`
  singleton (core/tools/__init__.py) on import. main.py imports each tool for
  its register side-effect; the router dispatches (tool, op, args); the REPL
  renders the faithful command line; permissions.classify() gates it; audit
  logs it. New tools slot into this UNCHANGED spine — they only ADD leaves.

  The one spine change is in permissions.py: the classifier's destructive
  taxonomy must learn the new verbs so the ADVISORY OpSpec class and the
  AUTHORITATIVE gate agree. This is the single load-bearing, cross-cutting edit.

Affected services
  - core/tools/*      (~44 new leaf modules)   — the bulk of the work
  - core/agent/permissions.py                   — destructive-taxonomy extension
  - core/agent/main.py                          — import/register wiring
  - finetune/scenarios/*, finetune/simulate/*   — training-data slices per tool
  - finetune/scenarios/__init__.py, simulate/__init__.py, coreimports.py,
    validate.py                                 — aggregator + threshold wiring
  - tests/test_tools_*                          — per-tool tests

Data flow (unchanged spine; new leaves)
  English request
    -> collector/context -> prompt -> Ollama (localhost, I1)
    -> router: (tool, op, args)                         [NEW tools resolvable here]
    -> repl.synthesize_command() renders faithful argv  [NEW argv shapes rendered]
    -> permissions.classify(argv)                       [EXTENDED taxonomy, Phase 1]
       READ->ALLOW | WRITE->CONFIRM | DESTRUCTIVE->CONFIRM_TYPED/REFUSE
    -> registry.dispatch -> tool.execute(op,args)       [NEW leaves execute here]
    -> run_subprocess(argv) (local binary only, I1)
    -> ToolResult -> audit.jsonl (I4) -> user

Invariants this plan MUST preserve
  I1  No network. Tools shell out via run_subprocess to LOCAL binaries only;
      import NO python libraries that open sockets (no requests, no docker SDK,
      no psycopg — use the psql/mysql/podman CLIs).
  I2  No AI/LLM/model/agent language in ANY user-facing string (every ToolSpec/
      OpSpec description, every ToolResult.summary, every simulator summary).
      test_output_hygiene + assert_no_ai_language enforce this.
  I3  Tools NEVER call permissions.classify(); the caller resolves the gate.
  I4  Tools NEVER write audit records; the caller writes them.
  I6  Zero tier/product/model names anywhere in tool files.
  I9  execute() NEVER raises — every failure degrades to a well-formed
      ToolResult (see disk.py header).
  SELinux-aware: surface an AVC hint suffix when stderr looks like a denial
  (reuse the _SELINUX_HINT_RE / _maybe_selinux_hint pattern from services.py).
  Rocky 9: dnf not apt; systemd; SELinux enforcing; pin no ':latest'.

### PHASE 1: Permission Classifier Taxonomy Extension (permissions.py) + Security Gate
   Prerequisites: Phase 0 (destructive-verb manifest)
   Deliverables:
      - Extended destructive taxonomy in core/agent/permissions.py so every
        manifest verb classifies as DESTRUCTIVE, plus WRITE recognition for the
        new mutating verbs (so they don't sit at the default-deny floor with a
        generic reason). Concretely: add to _DESTRUCTIVE_PROGRAMS (stratis-,
        vgcreate no / pvcreate no — those are WRITE; but virsh/podman/semanage/
        setsebool handled with argv-aware sub-verb logic in _classify_argv),
        extend _classify_argv with per-verb blocks (virsh destroy/undefine,
        podman rm -f/rmi, stratis ... destroy, restic forget --prune, dropdb,
        realm leave, grubby --remove-kernel, at -r, crontab -r), and extend
        _WRITE_PATTERNS for the benign mutators (nmcli/podman run/semanage add).
      - New unit tests in tests/test_permissions.py covering EACH new verb at
        the DESTRUCTIVE boundary AND its safe read/write siblings (e.g. `podman
        ps` READ, `podman run` WRITE, `podman rm -f` DESTRUCTIVE).
      - Adversarial security review verdict (consensus-verification-duo).
   Steps:
      1. For each manifest verb, add the narrowest argv-aware rule in
         _classify_argv that ESCALATES to DESTRUCTIVE (mirror the existing
         style: case-sensitive flags where it matters, e.g. `-f`/`--force`).
      2. Add WRITE recognition for the mutating-but-safe verbs so they read as
         "recognized state-changing operation" not "unrecognized ... for safety".
      3. Preserve default-deny: anything unrecognized still floors at WRITE.
      4. Write exhaustive boundary tests (READ/WRITE/DESTRUCTIVE per verb, plus
         non-interactive REFUSE for destructive).
      5. Hand the diff to a consensus-verification-duo to adversarially hunt for
         MISSED destructive shapes and OVER-gating regressions of existing verbs.
   Validation:
      - New test_permissions.py cases all green; existing permission tests still
        green (no regression to the 11 tools' gating).
      - classify("<verb> ...", ExecContext(interactive=False)) == REFUSE for
        every destructive manifest verb.
      - Duo returns consensus APPROVE with zero unresolved missed-verb findings.
   Risks / Edge cases:
      - Over-gating a benign read (e.g. `virsh list`) to WRITE annoys users but
        is safe; UNDER-gating a destructive verb is catastrophic on a live box.
        Bias toward escalation, exactly as the file's own comments instruct.
      - This file is edited ONLY here — do NOT let Phase 13 or any tool slice
        touch permissions.py (shared-file serialization).
   Subagent orchestration:
      - Execution shape: [SEQUENTIAL — depends on Phase 0]. Runs CONCURRENTLY
        with the tool-building waves (Phases 2-12) — tool files don't import the
        classifier, so there is no code coupling; only the final acceptance gate
        (Phase 14) depends on Phase 1 being merged.
      - REQUIRED subagent_type: general-purpose for authoring; then
        consensus-verification-duo for the security gate (adversarial dialectic
        is the whole point — inline self-review is FORBIDDEN here).
      - REQUIRED model: opus (authoring — correctness-critical, one missed verb
        cascades to data loss); consensus-verification-duo also on opus.
      - Run in background: yes (multi-minute; other waves proceed in parallel).
      - Brief template (authoring):
         "Execute Phase 1 of <PLAN_FILE_PATH>. Read
          runtime/audits/rhel-tools-complete/phase-0/DESTRUCTIVE-VERB-MANIFEST.md
          and core/agent/permissions.py in full. Touch ONLY permissions.py and
          tests/test_permissions.py. For each manifest verb add the narrowest
          argv-aware DESTRUCTIVE rule + boundary tests; preserve default-deny and
          the existing 11 tools' gating. Validation: new+existing permission
          tests green; non-interactive destructive == REFUSE. Produce the diff +
          test output as evidence. Print one-line summary and exit."
      - Brief template (gate): dispatch consensus-verification-duo AFTER
         authoring: "Adversarially review the Phase 1 permissions.py diff of
         <PLAN_FILE_PATH> against the DESTRUCTIVE-VERB-MANIFEST. Find missed
         destructive shapes and over-gated regressions. Return APPROVE/BLOCK +
         required fixes."

## 4. DATA MODEL CHANGES
   None. No DB, no Drizzle, no migrations, no RLS. The only "schema" is the
   in-code ToolSpec/OpSpec/ArgSpec dataclasses in core/tools/__init__.py, which
   are FROZEN and used AS-IS (additive registrations only).

## 5. API CONTRACT
   No HTTP API. The "contract" is the tool interface:
     execute(op: str, args: dict) -> ToolResult
   Every new tool binds to the frozen ToolResult (exit_code, stdout, stderr,
   summary) and registers a ToolSpec with per-op OpSpec(permission_class, args).
   The router/REPL/permissions/audit spine consumes this unchanged.

## 6. WORKER / QUEUE CHANGES
   None. Erdtree has no queue subsystem; tools execute synchronously via
   run_subprocess in the REPL turn.

## 7. FRONTEND CHANGES
   None. Terminal-native, no GUI (product invariant). The only user-visible
   surface is the ToolResult.summary line, which MUST be I2-clean.

## 8. TESTING STRATEGY
   Unit (per slice): tests/test_tools_<name>.py mirroring test_tools_services.py
     — patch core.tools.<name>.run_subprocess, assert command vectors, exit-code
     mapping, I2-clean summaries, SELinux-hint suffix on AVC stderr, and that
     execute() never raises (I9).
   Classifier: tests/test_permissions.py — READ/WRITE/DESTRUCTIVE boundary per
     new verb + non-interactive REFUSE for destructive (Phase 1).
   Integration: finetune/simulate + finetune/scenarios import-time asserts
     (completeness + schema-sync); finetune/validate.py replay through the LIVE
     router.
   Hygiene: test_output_hygiene / assert_no_ai_language over all new summaries.
   Manual QA (on mossad, DEFERRED-live): spot-run a handful of READ ops against
     the real Rocky/Arch box via `ssh mossad` to sanity-check argv shapes.

## 9. ROLLOUT & OBSERVABILITY
   Feature flag: none needed — tools are inert until the router routes to them;
     an unregistered tool is simply unreachable. New tools can be merged tool-by-
     tool (each slice is independently importable).
   Observability: the existing audit.jsonl captures every op (I4) unchanged.
   Rollback: remove the tool's import line from main.py (and its aggregator
     lines) — the leaf file is pure additive, so deletion is clean. Reverting
     Phase 1 permissions.py changes reverts gating only (never leaves a tool
     under-gated because default-deny floors at WRITE).

## 12. EXECUTOR ORCHESTRATION GUIDE

### 12.1 Parallelism map
   Phase | Execution           | Siblings | Depends on   | Model  | Subagent type
   P0    | SINGLE              | —        | none         | opus   | general-purpose
   P1    | SINGLE (+duo gate)  | —        | P0           | opus   | general-purpose -> consensus-verification-duo
   P2 A  | PARALLEL FANOUT     | 4        | P0           | sonnet | general-purpose
   P3 B  | PARALLEL FANOUT     | 5        | P0           | sonnet | general-purpose
   P4 C  | PARALLEL FANOUT     | 5        | P0           | sonnet | general-purpose
   P5 D  | PARALLEL FANOUT     | 3        | P0           | sonnet | general-purpose
   P6 E  | PARALLEL FANOUT     | 4        | P0           | sonnet | general-purpose
   P7 F  | PARALLEL FANOUT     | 6        | P0           | sonnet | general-purpose
   P8 G  | PARALLEL FANOUT     | 3        | P0           | sonnet | general-purpose
   P9 H  | PARALLEL FANOUT     | 3        | P0           | sonnet | general-purpose
   P10 I | PARALLEL FANOUT     | 4        | P0           | sonnet | general-purpose
   P11 J | PARALLEL FANOUT     | 3        | P0           | sonnet | general-purpose
   P12 K | PARALLEL FANOUT     | 4        | P0           | sonnet | general-purpose
   P13   | SINGLE (serialized) | —        | P2..P12 all  | sonnet | general-purpose
   P14   | SINGLE              | —        | P1, P13      | opus   | general-purpose

   DAG (non-linear):
                     ┌──> P1 (classifier) ──────────────┐
                     │                                   v
        P0 ──────────┼──> P2 A ┐                        P14 (accept)
                     │    P3 B │                          ^
                     │    ...  ├─(43 tool slices, 11 ── > P13 (wiring) ─┘
                     │    P12 K┘  parallel waves)
   P1 runs CONCURRENTLY with the tool waves (no code coupling); both must land
   before P14. P13 waits for ALL tool slices; P14 waits for P1 + P13.

   Fan-out ceiling: 44 slices total. Do NOT launch all 44 at once. Run the
   lettered waves as batches of <= ~12 concurrent siblings (A+B+part-C, etc.),
   or one letter at a time. Slices are additive/collision-free so the only real
   limits are token budget and host throughput, not Edit conflicts.

### 12.2 Cross-phase work consolidation
   - Each tool slice creates 4 files in ONE agent (tool + scenarios + simulator
     + test). This is deliberate: op names and arg schemas stay in-context, so
     INV-schema-sync and the simulator's op-coverage are correct by construction.
     Do NOT split a tool's scenario/simulator into separate agents — that forces
     a re-read of the ToolSpec and invites drift.
   - ALL slices read the SAME two inputs: SLICE-CONTRACT.md and
     core/tools/services.py. These are small; per-slice re-reads are fine (no
     need to pre-distill).
   - The 5 shared registration files (main.py, scenarios/__init__.py, simulate/
     __init__.py, coreimports.py, validate.py) are touched ONLY in P13, by ONE
     agent, SEQUENTIALLY — never by a tool slice (Edit-collision + completeness-
     assert ordering).
   - permissions.py is touched ONLY in P1, by ONE agent — never by a tool slice.

### 12.3 Model-mix budget
   - Fable: 0 phases. The one correctness-critical phase (P1 classifier) is
     handled by opus AUTHORING + a consensus-verification-duo adversarial gate,
     which catches missed-verb cases better than a single smarter pass would.
     No phase requires frontier-grade solo reasoning.
   - Opus: P0, P1, P14 (+ the duo runs on opus). ~3 of 15 phases (~20%) —
     justified: whole-surface manifest, security-critical taxonomy, final gate.
   - Sonnet: all 11 tool waves + P13 wiring. ~73%.
   - Haiku: 0 — every slice has real logic (arg schemas, SELinux hints, exit-code
     mapping); haiku would produce brittle tool code.
   Rough split: 0% fable / ~20% opus / ~80% sonnet / 0% haiku.

### 12.4 Estimated wall-clock
   Best case (full parallelism, waves batched ~12-wide, P1 concurrent):
     P0 (~5m) -> [P1 ~15m ∥ tool waves ~4 batches x ~8m = ~32m] -> P13 (~8m)
     -> P14 (~10m)  ≈ 55-60 minutes.
   Strictly serial (one slice at a time, 44 slices x ~7m + P0/P1/P13/P14):
     ≈ 6-7 hours.
   Critical path: P0 -> tool waves (longest batch) -> P13 -> P14. P1's duo gate
   runs alongside and must be APPROVE before P14 accepts.

### 12.5 Failure recovery policy
   - Tool slice (P2-P12) fails its own tests: retry up to 2x with the same
     sonnet subagent (non-flaky; usually an arg-schema or I2-string fix). On 3rd
     failure, log a deferred-item and continue — one missing tool does not block
     the others (but P13's completeness assert will flag it).
   - P1 classifier duo returns BLOCK: PAUSE and escalate to user — a missed
     destructive verd is a safety call, not an auto-retry.
   - P13 completeness assert fails (a tool op has no simulator): bounce to that
     tool's slice agent to add the missing simulator op; do NOT stub it in the
     aggregator.
   - P14 validate.py < coverage or MISS-rate over threshold: bounce to the
     offending tool's slice to add scenarios; re-run.
   - Default (unspecified failure): pause and escalate.
