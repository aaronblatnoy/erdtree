## 0. CONTEXT & GOALS

Problem statement
-----------------
Erdtree's tool-call reliability is decision #2 / the #1 technical bet
(docs/decisions/0002 §freeze, bench/README.md). Base Qwen2.5 speaks generic
function-calling but does not natively know Erdtree's frozen §1 wire shape
(one function per tool, `operation` enum + per-op arg union), the I2-clean
house voice, or the confirm-before-write discipline. We raise the tool-call
validity rate by fine-tuning on high-quality traces that demonstrate the
EXACT protocol and style, generated by Claude wearing Erdtree's real system
prompt and real tool schemas.

Success criteria (measurable)
-----------------------------
- `python -m finetune.generate --n 600 --tier radagon` produces
  finetune/data/traces.jsonl with >= 600 complete multi-turn records.
- `python -m finetune.validate finetune/data/traces.jsonl` reports
  MISS rate <= 0.5% (exit 0), every tool_call validating against the LIVE
  `router.validate_arguments()` (not a reimplementation).
- Coverage: every one of the 11 registered tools appears; READ/WRITE/
  DESTRUCTIVE permission classes all represented; single-op / multi-step /
  diagnostic complexities all represented.
- ZERO I2-forbidden terms ("AI","LLM","model","agent","ollama","inference",
  etc.) in any assistant `content` string across the corpus.
- The whole pipeline (scenarios -> convert -> validate) runs OFFLINE with a
  Fake LLM backend and no network / no ANTHROPIC_API_KEY (test + smoke path).

Non-goals (explicitly out of scope)
-----------------------------------
- Running the actual fine-tune (TRL/Unsloth) on the mossad server — this plan
  produces the DATA; training is a separate downstream job.
- Building the Ollama Modelfile / GGUF conversion that loads the fine-tuned
  weights — separate plan.
- Any change to core/ tool schemas, the house prompt, router, or 0002. This
  pipeline is a READ-ONLY CONSUMER of core/; if a schema is wrong, fix it in
  core/, never in finetune/.
- RLHF / DPO / preference data. SFT traces only.

Assumptions made
----------------
- A1. Generation runs on the dev Mac with `pip install anthropic tqdm`. The
      Anthropic API key is supplied via ANTHROPIC_API_KEY env (never hardcoded,
      never committed).
- A2. Generation model is `claude-sonnet-4-6` (exact model-id string, no date
      suffix — verified against the claude-api skill model table). Overridable
      via --claude-model.
- A3. The 11 registered tools are: services, packages, logs, network, firewall,
      users, disk, processes, hardware, files, docs. Confirmed by the import
      block in core/agent/main.py (services/packages/logs + Phase-6 network/
      firewall/users/disk/processes/hardware/files) plus docs. The pipeline
      imports the LIVE registry rather than hardcoding this list; the count is
      asserted, not assumed.
- A4. "tier" affects only which system-context depth / persona (tier_prompt)
      is injected and the target model size label written into trace metadata —
      NOT the trace structure (CLAUDE.md invariant 7, prompt.py I6). marika and
      radagon share one trace format.
- A5. Anthropic tool_use ids use the `toolu_` prefix; these map 1:1 onto the
      OpenAI `tool_calls[].id` we emit and the `tool` message `tool_call_id`.
      We do NOT reuse §2's `call_abc123` example ids — we carry Claude's ids
      through verbatim so correlation is preserved.
- A6. Traces are single-tool-call-per-assistant-turn by default (matches the
      few-shot discipline in prompt.py: "One operation at a time when the next
      step depends on the result"). Parallel tool_calls in one turn are allowed
      by 0002 §2 but are NOT synthesized in v1 to keep small-base learning clean.

## 1. ARCHITECTURE OVERVIEW

How this fits
-------------
finetune/ is a NEW top-level sibling of core/, rag/, bench/, models/. It is a
build-time data factory, not shipped in the ISO. It imports FROM core/ (the
single source of truth for schemas, the house prompt, and validation) and
never the reverse. Its output (JSONL) feeds a downstream trainer on mossad.

Data flow
---------
                        core/ (SOURCE OF TRUTH — never mutated)
                        ├─ tools registry (11 self-registered ToolSpecs)
                        ├─ prompt._HOUSE_SYSTEM_PROMPT + assemble_messages()
                        ├─ router.registry_schemas() / validate_arguments()
                        └─ permissions.OpClass
                                   │  (import only)
                                   ▼
  finetune/coreimports.py  ── thin, single re-export seam ──┐
                                                            │
  scenarios/ ─┐                                             │
  context.py ─┤ (fixtures: what to ask, on what host)       │
  simulate/  ─┘ (fake but realistic Rocky-9 tool outputs)   │
                    │                                        │
                    ▼                                        ▼
  generate.py  ──uses──►  llm.py (LLM seam: Fake default / Anthropic real)
      │  1. build real messages array (house prompt + real §1 tool list)
      │  2. Claude returns Anthropic tool_use block(s)
      │  3. convert.py: Anthropic tool_use -> OpenAI tool_calls
      │  4. simulate.py: inject realistic tool result -> role:"tool"
      │  5. Claude returns final English answer
      │  6. append record to finetune/data/traces.jsonl
      ▼
  validate.py  ──replays every tool_call through router.validate_arguments()──►
                 report: total / valid / MISS-rate / per-tool coverage

Invariants this plan must preserve
----------------------------------
- INV-I2 (no AI language): every synthesized/returned assistant `content`
  string, and the injected system prompt, must pass prompt._AI_PATTERN.
  simulate.py summaries and any hand-written text must be I2-clean.
- INV-0002 (frozen wire format): emitted records MUST match 0002 §1/§2/§3
  exactly — `tool_calls[].type=="function"`, `function.arguments` is a
  JSON-ENCODED STRING (not a nested object), `tool` messages correlate by
  `tool_call_id`. validate.py is the enforcement gate.
- INV-schema-sync: NEVER hardcode a tool schema. Always derive from the live
  registry via router.registry_schemas() so the corpus tracks core/ drift.
- INV-permission-fidelity: WRITE/DESTRUCTIVE scenarios must show the
  confirm-before-execute pattern (a confirmation turn precedes the write
  tool_call), matching permissions.OpClass semantics (READ->immediate,
  WRITE->confirm, DESTRUCTIVE->typed "DESTROY"). Otherwise the model learns
  to skip the gate — a safety regression (CLAUDE.md invariant 3).
- INV-offline (Fake default): the LLM is behind a seam; the Fake backend is
  the default in tests and the offline smoke path. No network, no key required
  to build/validate. (Mirrors the repo's server-imminent Fake-default posture.)
- INV-data-gitignored: finetune/data/ MUST be gitignored (large/generated).

### PHASE 1: scenarios/ package — the 600+ scenario corpus (fan-out by tool)
   Prerequisites: Phase 0
   Deliverables:

      2. Author >= 60 scenarios/tool spread across the tool's real ops and the
         three complexities. Cover the domains named in spec: service mgmt,
         package mgmt, log analysis, network diag, firewall rules, user admin,
         disk health, process mgmt, hardware inventory, file ops, security
         hardening (hardening scenarios span firewall/users/services).
      3. Set permission_class to match the op's REAL declared class (do not
         guess) so WRITE/DESTRUCTIVE scenarios are honestly labeled.
   Aggregator/join step (SEQUENTIAL, after all siblings):

### PHASE 4: convert.py + llm.py — the format-conversion crux and the LLM seam
   Prerequisites: Phase 0
   Deliverables:
      - finetune/convert.py (PURE, no I/O):
        * anthropic_tool_use_to_openai_tool_calls(blocks) ->
            {"role":"assistant","content":None,"tool_calls":[
              {"id": tu.id, "type":"function",
               "function":{"name": tu.name,
                           "arguments": json.dumps(tu.input, separators=(',',':'))}}]}
          (input DICT -> arguments JSON STRING; 0002 §2 — string, not object.)
        * anthropic_tool_result_to_openai_tool_msg(tool_use_id, result_dict) ->
            {"role":"tool","tool_call_id": tool_use_id,
             "content": json.dumps(result_dict, separators=(',',':'))}
          (0002 §3 compact-JSON body.)
        * assistant_text_to_openai(text) -> {"role":"assistant","content":text}
        * assemble_record(system, tools, messages) -> the final ShareGPT record
          (system message carrying HOUSE_SYSTEM_PROMPT + tier + context; the
          `tools` array in §1 format stored alongside for trainer visibility).
      - finetune/llm.py (the seam):
        * LLMBackend Protocol: async def complete(messages, tools, tool_choice)
          -> normalized {stop_reason, content_blocks} (Anthropic-shaped).
        * FakeBackend (DEFAULT): deterministic — given a scenario it returns a
          canned tool_use block for the scenario's (tool, operation, plausible
          args) then, on the follow-up call, a canned I2-clean English answer.
          Enables OFFLINE build/validate/smoke (INV-offline).
        * AnthropicBackend: wraps `anthropic.AsyncAnthropic()`; calls
          client.messages.create(model=..., max_tokens=~1024, system=..,
          messages=.., tools=.., tool_choice={"type":"auto"}). Parses
          response.content for type=="tool_use" and type=="text" blocks;
          checks stop_reason=="tool_use" vs "end_turn". Relies on the SDK's
          built-in retry for 429/5xx. (No thinking config needed; if added,
          use {"type":"adaptive"} only — never budget_tokens on sonnet-4-6.)
   Steps:
      1. Implement convert.py first; it is the correctness core. Guarantee
         `arguments` is always a JSON string, ids flow through verbatim, and
         `content` is None on tool-call turns (0002 §2).
      2. Implement llm.py with FakeBackend default. AnthropicBackend behind
         `if backend == "anthropic"`. Never import anthropic at module top in a
         way that breaks offline import — import lazily inside AnthropicBackend.
      3. Unit tests (tests/finetune/test_convert.py): round-trip a known
         Anthropic tool_use -> OpenAI tool_calls -> feed through
         router.validate_arguments() (via coreimports) and assert VALID;
         assert arguments is `str`; assert tool_call_id correlation holds.
   Validation:
      - `python -c "import finetune.convert, finetune.llm"` imports with NO
        anthropic installed / no key (lazy import proven).
      - test_convert.py green: every converted call validates through the LIVE
        router; arguments is a JSON string; ids correlate.
   Risks / Edge cases:
      - THE classic bug: emitting arguments as a nested object instead of a
        JSON string -> router MISS on every trace. Guarded by the explicit
        str assert + router replay in tests.
      - Claude returning prose-only (no tool_use) on an act-scenario -> that
        turn is a MISS by 0002 §5. generate.py (Phase 5) must detect and either
        re-ask (§5 flow) or drop the trace; convert.py just faithfully reflects
        what came back.
      - Non-ASCII / forward-slash escaping differences in Claude tool inputs —
        parse with json, never string-match (claude-api pitfall). Since WE
        json.dumps the parsed dict, escaping is normalized on our side.
   Subagent orchestration:
      - Execution shape: [SINGLE] (parallel with Phases 1-3)
      - REQUIRED subagent_type: general-purpose
      - REQUIRED model: opus (correctness-critical; a subtle error here poisons
        the ENTIRE corpus silently)
      - Run in background: no (Phase 5 blocks on it)
      - Brief: "Execute Phase 4 of <PLAN_FILE_PATH>. Build finetune/convert.py
        (pure) and finetune/llm.py (LLMBackend Protocol + FakeBackend default +
        lazy-import AnthropicBackend using anthropic.AsyncAnthropic, model
        claude-sonnet-4-6). Read PHASE 4 + docs/decisions/0002 sections 2 and 3.
        Touch only those two files + tests/finetune/test_convert.py. CRITICAL:
        tool_calls[].function.arguments is a JSON STRING; ids flow verbatim;
        content is None on tool-call turns. Validation: converted calls pass the

      2. For each scenario: make_context(tier,seed) -> snapshot_text; build the
         real messages via assemble_messages(PromptConfig(tier_prompt, snapshot_text,
         user_input=scenario.user_input, tools=live_tool_list(), tool_choice="auto")).
      3. Call backend.complete(...) -> tool_use block(s). convert to OpenAI
         assistant turn. For WRITE/DESTRUCTIVE scenarios, model the confirm turn
         (INV-permission-fidelity): if the op's OpClass != READ, insert the
         user confirmation ("yes" / typed "DESTROY") before the executing call,
         so the trace teaches the gate.
      4. simulate(tool, op, args, ctx) -> ToolResult; convert to role:"tool".
      5. Call backend.complete(...) again with the tool result appended ->
         final English answer; convert to assistant content turn. Assert
         assert_no_ai_language on that content (drop/regenerate on violation).
      6. On a MISS from Claude (prose where a tool was required), follow 0002 §5:
         append the router re-ask and retry once; if still a MISS, DROP the trace
         and log it (do not emit a broken record).
      7. Write each complete record as one JSONL line. Concurrency via
         asyncio.Semaphore(K) over an AsyncAnthropic client (optionally the
         aiohttp backend for higher throughput). --resume: count existing lines,
         skip already-produced scenario ids. tqdm progress bar over N.
   Validation:
      - OFFLINE: `python -m finetune.generate --n 20 --backend fake
        --out /tmp/smoke.jsonl` writes 20 well-formed records with no network.
      - Each record: first message role=="system" and content contains the
        house prompt; assistant tool-call turns have string arguments; tool
        turns correlate; final assistant content is I2-clean.
      - LIVE (manual, key present): `--n 50 --backend anthropic` produces 50
        records; spot-check 5 by eye.
   Risks / Edge cases:
      - Rate limits / 429 on large --n. Mitigation: rely on SDK auto-retry +
        modest --concurrency default (5); document raising it cautiously.
      - Partial write / crash mid-run. Mitigation: append-per-record + --resume
        by scenario id; never hold the whole corpus in memory.
      - Cost. Mitigation: --n small by default in examples; Fake backend for CI.
      - tier must not change trace STRUCTURE (A4). Mitigation: tier only feeds
        tier_prompt + context depth + a metadata field.
   Subagent orchestration:
      - Execution shape: [SEQUENTIAL — depends on Phases 1,2,3,4]
      - REQUIRED subagent_type: general-purpose
      - REQUIRED model: opus (async orchestration + §5 re-ask flow + permission
        gate modeling; multi-file reasoning across convert/llm/simulate/context)
      - Run in background: no (its output gates Phase 6 run + Phase 8 gate)
      - Brief: "Execute Phase 5 of <PLAN_FILE_PATH>. Build finetune/generate.py
        (+__main__ CLI). Read PHASE 5 + section 1 flow + convert.py/llm.py APIs.
        Touch only finetune/generate.py. Use assemble_messages with the LIVE

### 12.1 Parallelism map

   P0    | SINGLE           | —        | none              | sonnet | general-purpose
   P1.*  | PARALLEL FANOUT  | 10       | P0                | sonnet | general-purpose
   P1.j  | SINGLE (join)    | —        | all P1.*          | sonnet | general-purpose
   P2    | SINGLE           | —        | P0                | sonnet | general-purpose
   P3.*  | PARALLEL FANOUT  | 10       | P0                | sonnet | general-purpose
   P3.j  | SINGLE (join)    | —        | all P3.*          | sonnet | general-purpose
   P4    | SINGLE           | —        | P0                | opus   | general-purpose
   P5    | SINGLE           | —        | P1.j,P2,P3.j,P4   | opus   | general-purpose
   P6    | SINGLE           | —        | P0 (run: P5)      | sonnet | general-purpose

   DAG sketch:
                    ┌─ P1.* (x10) ─ P1.j ─┐
        P0 ──┬──────┼─ P2 ───────────────┤
             │      └─ P3.* (x10) ─ P3.j ─┤
             └─ P4 ─────────────────────── P5 ─ P6 ─┐
                └───────────────────────────────────┴─ P8 ─ (P7 anytime after P4-6)

### 12.2 Cross-phase work consolidation
   - Every phase imports finetune/coreimports.py — P0 MUST land first and is a
     hard prerequisite for all others. Do not start any fanout before P0 is green.
   - scenarios/ and simulate/ are PACKAGES precisely so their fanouts never edit
     a shared file. The two SEQUENTIAL join steps (P1.j, P3.j) are the ONLY
     writers of the respective __init__.py — never fan those out.
   - P1 and P3 both fan out 10 siblings. Running both fanouts fully concurrently
     = 20 live agents (under the ~25 soft ceiling but near it). RECOMMENDED:
     launch P1's fanout, then P3's fanout, so peak concurrency stays ~10; P2
     (single) can ride alongside either. All three trees depend only on P0.
   - P4 (opus) can run concurrently with the P1/P2/P3 sonnet trees — different
     files, different model tier, no contention.

### 12.3 Model-mix budget
   Target split across the ~24 dispatchable units (2x10 siblings + joins + singles):
     - fable:  0%  (no phase is frontier-grade; the crux is opus-adequate)
     - opus:  ~12% (P4 convert-crux, P5 driver, P8 gate — the correctness spine)
     - sonnet: ~80% (all data-authoring siblings, joins, P0, P2, P6)
     - haiku:  ~4%  (P7 README only)
   Sanity: no opus on trivial data authoring; no haiku on the router-facing
   validate or the format converter. Zero fable is expected for this plan.

### 12.4 Estimated wall-clock
   Best case (parallel): P0 (~5m) -> [P1/P2/P3 fanouts + P4 concurrent ~15m] ->
     P5 (~10m) -> P6 (~5m) -> P8 (~10m)  ≈ 45 min, plus P7 (~3m) off critical path.
   Worst case (strictly serial): ~2.5–3 hours.
   Critical path: P0 -> P4 -> P5 -> P6 -> P8 (the P1/P2/P3 trees must merely
   finish before P5's join, and they parallelize).
   NOTE: wall-clock excludes any LIVE --backend anthropic corpus run (cost/time
   is operator-driven; the build + gate use the offline Fake backend).

### 12.5 Failure recovery policy
   - P0: retry up to 2x; if the 11-tool assert fails, STOP and escalate (a core/
     import regression, not a finetune bug).
   - P1.*/P3.* siblings: retry up to 2x each (independent, non-flaky). A single
     failed sibling does NOT block others; the join (P1.j/P3.j) will fail its
     coverage/completeness assert and surface the gap — re-dispatch just that
     tool's sibling, then re-run the join.
   - P4: on failure retry once; if convert still can't pass the router replay,
     PAUSE and escalate (likely a 0002 misreading — human check).
   - P5: retry up to 2x; if the offline fake smoke still can't produce
     well-formed records, escalate (blocks P6/P8).
   - P6: retry up to 2x.
   - P8 (gate): on BLOCK, route the concrete fix list back to P4/P5/P6 and
     re-run P8 — do NOT override a BLOCK. Genuine unresolved split -> escalate.
   - Default (unlisted): pause and escalate.
